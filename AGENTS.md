# Hideout Coffee POS

Laravel 12 point-of-sale app (coffee shop) with two roles: `owner` (admin + own POS) and `kasir` (cashier). All UI is Indonesian.

## Stack

- **Laravel 12** + **MySQL** (`hideout_coffe`); session/queue/cache all `database` driver
- **Blade** (`@yield` section pattern) + **Tailwind v3** (PostCSS) + **Chart.js / SweetAlert2 / animate.css / anime.js from CDN** + **Alpine.js** + **Preline UI**
- **Spatie RBAC** — 2 roles, `owner` and `kasir`; `role` middleware aliased in `bootstrap/app.php:18`
- **No API routes**; web-only. `routes/web.php` `require`s `routes/auth.php`. The "API" endpoints are JSON filters on web routes.
- `barryvdh/laravel-dompdf` for all PDF output

## Architecture

- **Owner** (`/owner/*`, `role:owner`): `Owner\DashboardController` (invokable), `CategoryController`, `MenuController`, `CashierController`, `PromoController` (all `Route::resource`; menus, cashiers and promos additionally have a `toggle-status` PATCH — categories does **not**), plus `Owner\TransactionController` with **hand-written** routes — `index`, `index-filter`, `chart-filter`, `print-index`, `create`, `store`, `page` (`?tab=create|history`), `history`, `history-filter`, `load-more-menus`, `show`, `kasir-show`, `receipt-pdf`, `cancel`. Owner sees **all** transactions on `/owner/transactions` (global stats, `cashier_id` filter over `User::role(['kasir','owner'])`) — but the `history`/`history-filter` routes are scoped to `Auth::id()`.
- **Kasir** (`/kasir/*`, `role:kasir`): `Cashier\DashboardController` (invokable) + `Cashier\TransactionController` (create, store, cancel, history, history-filter, show, load-more-menus, receipt-pdf). **Views live in `resources/views/cashier/`** (there is no `views/kasir/`). The kasir dashboard's today-counts, chart and recent transactions are scoped to `Auth::id()`; top-5 products and active-menu count are **global**.
- `owner.kasir.dashboard` (`GET /owner/kasir-dashboard`) runs `Cashier\DashboardController` against the same `cashier.dashboard` view — the owner's kasir-mode landing page, not the admin dashboard. ⚠ `$isOwner` is **not** passed by the controller; the view self-derives it at `cashier/dashboard.blade.php:4` via `Auth::user()->hasRole('owner')`. Every shared kasir view does this — never expect the controller to supply it.

### Shared partials — edit one, you change both

- Owner's `history()`/`historyFilter()` render the **kasir** views (`cashier.transactions.history`, `cashier.transactions._history_table`), scoped to `Auth::id()`, with links flipped via `$isOwner`: owners → `owner.transactions.kasir-show` (`kasirShow()` renders `cashier.transactions.show`), kasir → `kasir.transactions.show`.
- ⚠ `Owner\TransactionController::page()`'s history tab is **not** that partial — it is a separate inline table in `owner/transactions/page.blade.php` (same `Auth::id()` scope, hardcoded `owner.transactions.show` links). Changes to `_history_table` do **not** propagate; keep them in sync by hand.
- `index()`/`indexFilter()` share `transactionsQuery()` and `owner/transactions/_data_table.blade.php`; `printIndex()` reuses the same query.
- The promo menu picker is shared via `resources/views/owner/promos/_menu_multi_select.blade.php` (included by both `owner/promos/{create,edit}.blade.php`); it owns the `menuMulti()` Alpine component and the `JSON_HEX_TAG`-encoded menu payload.

### Ownership guards are asymmetric

`Owner\TransactionController::show()`/`kasirShow()`/`receiptPdf()`/`cancel()` have **no** `user_id` check. `Cashier\TransactionController::show()`/`receiptPdf()`/`cancel()` **do** (`$transaction->user_id !== Auth::id()` → 403). Mirror the existing side when adding a shared feature.

### Domain notes

- **`User` has no `name` column** — migration `2026_04_09_020920_modify_users_table.php` renamed it to `username` and added `first_name`/`last_name`/`status`. Use `$user->full_name` (accessor, falls back to `username`) or `avatar_url` (falls back to `images/logo-ho.png` — use it instead of hardcoding the logo). `phone` and `photo` came in later migrations.
- **Login is by `username`** (`app/Http/Requests/Auth/LoginRequest.php`). `AuthenticatedSessionController::store()` rejects `status === 'inactive'` (logout + error on the `username` field) and redirects by role: owner → `owner.dashboard`, kasir → `kasir.dashboard`. `LoginRequest::messages()` supplies Indonesian messages, and `auth/login.blade.php` merges the two required-field errors into one ("Username dan password wajib diisi.") — keep them in sync. Forgot/reset password (Breeze) still uses **email**.
- **Menu `code`**: nullable unique, auto-generated by `Menu::generateCode()` as `{CATEGORY-INITIALS}-###` (e.g. `KO-001`), counted per category. The menus index orders by `code`. `Menu::reindexCodes()` renumbers a category after a delete or a move between categories — `MenuController` calls it in `update()` and `destroy()`; don't skip it.
- **Transaction `code` is derived, not stored**: `Transaction::getCodeAttribute()` → `TRX-0003` plus `-XX` per unique category (first 2 chars, uppercased), e.g. `TRX-0003-KO-NO`. ⚠ The suffix only appears when the `items` relation is loaded — the accessor checks `relationLoaded('items')`. Eager-load `items.menu.category` or you get a bare `TRX-####`.
- **`transactions.customer_name`** is nullable (migration `2026_10_21_000000_add_customer_name_to_transactions_table.php`). All 3 POS views (cashier create, owner create, page.blade) post it via a hidden input bound to Alpine `customerName`, validated `nullable|string|max:255` in both `store()` methods, and persisted in `localStorage` `pos_state.customerName`. Views displaying it: "Pelanggan" column in `_history_table`, `_data_table`, page.blade's inline history table (colspan 8), the print laporan and both dashboards; "Pelanggan:" line in both `show.blade.php` (`@if` guarded) and the receipt (`ReceiptBuilder` payload key `customer_name` + `@if (!empty(...))` in `pdf/receipt.blade.php`). The POS input's persist handler must be `savePosState()` — not `saveCart()`, which writes only `pos_cart`.
- **Menu photos** live on the `public` disk under `menus/{category-slug}/`; old files are deleted on update/destroy. Views render `$menu->thumb_url`, a **WebP thumbnail** generated by a `Menu::saved` hook via `app/Console/Commands/GenerateMenuThumbnails.php`; `getThumbUrlAttribute()` falls back to the original if the thumb is missing.
- **Profile** is shared by both roles and lives *outside* the `owner.`/`kasir.` groups: `profile.edit`/`profile.update` + a separate `profile.photo` route (`ProfileController::updatePhoto()` → `avatars/` on the `public` disk, old file deleted on replace, `image|mimes:jpg,jpeg,png,webp|max:2048`, auto-submits on file select). Password posts to `password.update` with the `updatePassword` error bag. `profile.destroy` exists with no UI. The old Breeze partials and `delete-user-form` were deleted; the header dropdown and the **kasir** sidebar link `profile.edit`.
- **`User` uses `SoftDeletes`** (migration `2026_10_18_000000_add_soft_deletes_to_users_table`). `CashierController::destroy()` soft-deletes with **no** `transactions()->exists()` guard (transactions are preserved — FK `transactions.user_id` is `onDelete('cascade')`, so a hard delete would wipe them) and blocks deleting your own account. `Transaction::user()` carries `->withTrashed()` — without it, `$transaction->user` resolves to `null` for a deleted kasir and the receipt PDF (`ReceiptBuilder:20`) and both `show.blade.php` views crash. `unique:users` validation still reserves a deleted kasir's username (query-builder unique counts trashed rows). Kasir terhapus otomatis hilang dari daftar kasir dan dropdown filter (`User::role(...)` kena global scope).
- **`Category` uses `SoftDeletes`** (migration `2026_10_18_000001`), same rationale: FK `menus.category_id` is `cascadeOnDelete()` — a hard delete would wipe menus. `CategoryController::destroy()` has **no** `menus()->exists()` guard and the index view always shows `confirmDelete` (the old `blockedDelete` branch is gone — it blocked the form in the browser, which is exactly how the kasir bug bit). `Menu::category()` and `Promo::category()` carry `->withTrashed()`; `Menu::reindexCodes()` uses `Category::withTrashed()->findOrFail`; `MenuController::store()`/`update()` use `Category::withTrashed()->find` (photo dir slug + `generateCode`). `MenuController::index()` loads `Category::withTrashed()` and groups by category **name** via `mapWithKeys` — menus of a deleted category stay visible/editable; `MenuController::edit()` and `PromoController::edit()` push the menu's/promo's current (ghost) category into the dropdown so saving doesn't silently reassign it. Deliberate: `unique:categories` **still counts trashed rows** (there is no DB unique index; reservation is chosen so two same-name groups can't collide in the name-keyed menus index, and for parity with username reservation). POS category chips (`Category::has('menus')`) exclude ghosts; ghost menus still appear in the unfiltered card grid and `load-more-menus`.
- **`Menu` uses `SoftDeletes`** (migration `2026_10_19_000000_add_soft_deletes_to_menus_table`). `MenuController::destroy()` soft-deletes (transaction-existence guard removed), nulls the `code` first, and calls `Menu::reindexCodes()` on the category — it does **not** delete photo/thumbnail files (same rationale as `CashierController::destroy()`: history/receipts must keep rendering the image; the old file-cleanup block was removed after it broke receipts). `TransactionItem::menu()` carries `->withTrashed()` so historical transactions still resolve the menu. Trashed menus are not returned by default queries (POS filters `status='active'` and normal listings) — they remain hidden from selling but preserved for history/receipts. `TransactionItem` also uses `SoftDeletes` (migration `2026_10_19_000001`) to preserve item history when a menu is soft-deleted. ⚠ `menus_code_unique` is a plain unique index — it **counts trashed rows**. `reindexCodes()` therefore nulls every code in the category (including trashed, via a `withTrashed()` update) before reassigning the non-trashed ones; `generateCode()` instead skips collisions with a `Menu::withTrashed()->where('code', $code)->exists()` bump loop. Without one of those, a reindex hits `UniqueConstraintViolationException` on `KO-###`. ⚠ **Never `forceDelete()` a menu that has transaction items** — `transaction_items.menu_id` FK is `onDelete('cascade')` (`2026_07_16_000001`), so a hard delete permanently destroys item history at the DB level (this actually happened once during debugging; recovery required re-running `TransactionSeeder`).
- **`Promo` uses `SoftDeletes`** (migration `2026_10_20_000000_add_soft_deletes_to_promos_table`). `PromoController::destroy()` has **no** `transactions()->exists()` guard (the old guard and the `blockedDelete` branch in `_promo-card.blade.php` were removed — the card now always shows the menu-style confirm: "…Data transaksi yang sudah ada tidak akan terhapus."), and the `withCount('transactions')` that fed it is gone from `index()`. `Transaction::promos()` carries `->withTrashed()` so receipts (`ReceiptBuilder` loads `promos`) and both `show.blade.php` views keep the promo line + pivot `discount_amount` after the promo is trashed — without it the receipt's promo list silently shrinks and can't reconcile with `promo_discount`. `Promo::active()` (the only promo read path in POS `create()`/`store()`) is scoped by the global soft-delete scope, so a deleted promo stops applying to new transactions (same user-visible behavior as bug #7 for expired promos). `transaction_promos.promo_id` is `cascadeOnDelete`, but soft delete never fires it — pivot rows survive. Promo `name` has no `unique` rule, so there is nothing to reserve.

## POS / discounts

Three discount layers, applied in this order: per-item flat discount → auto promos → manual transaction discount.

Promo/discount math is **duplicated across 5 files — change all of them**: the Alpine `posApp()` in `cashier/transactions/create.blade.php`, `owner/transactions/create.blade.php`, and `owner/transactions/page.blade.php`, plus the server recalc in `Cashier\TransactionController::store()` and `Owner\TransactionController::store()`. The server revalidates everything through `Promo::active()` + `calculatePromoDiscount()` and **the server wins** — the client figures are never trusted.

- Promos are `percentage` or flat `value`, scoped to `item` / `category` / `transaction`, gated by `min_quantity` / `min_amount`, and windowed by `start_date`/`end_date` (both `datetime` after migration `2026_09_20_000000_make_promos_dates_datetime`; null = unbounded). **Item scope targets a set of menus** via the `promo_menus` pivot (migration `2026_10_20_000001`, backfilled from old `target_id` then nulled; form posts `menu_ids[]`, validated `required_if:scope,item|array|min:1` + `exists:menus,id`, synced in `PromoController::store()`/`update()`); `promos.target_id` is now **category scope only**. `Promo::menu()` is gone — use `Promo::menus()` (`belongsToMany` + `withTrashed()` so ghost targets still render). Everywhere `$promos` is fetched for POS/display must eager-load `menus` (the 3 `@json($promos)` POS payloads and both `store()` recalc queries do) — the client math filters `cartItems` against `promo.menus` ids, and the server `calculatePromoDiscount()` item branch matches `(int) $item['menu_id']` against `$promo->menus->pluck('id')`.
- Cart and applied promos post as **JSON strings in hidden inputs** (`JSON.stringify(...)`); `store()` detects strings and `$request->merge(json_decode(..., true))` before validating.
- Payment methods: `cash`, `debit`, `kredit`, `transfer`, `qris` — validated in that exact `in:` list in both `store()` methods (`card` was renamed to `kredit` by migration `2026_09_21_175209_...`). The UI order in the "Metode Pembayaran" grid is **CASH → DEBIT → KREDIT → TRANSFER → QRIS** and must stay that way. Debit and kredit share the EDC modal; QRIS shows `public/images/qris.jpeg` and forces `amount_paid = total`. `transfer` opens its own **modal detail bank** (present in all three POS views: `cashier/transactions/create.blade.php`, `owner/transactions/create.blade.php`, `owner/transactions/page.blade.php`) with a bank picker + account number + nominal, and a "Sudah Dibayar" button that sets `amountPaid = total` and continues to the confirm modal (or submits directly on `page.blade.php`, which has no confirm modal). The bank list lives in **`config/hideout.php`** (`bank_accounts`, each entry `bank` / `account_number` / `account_name`) and is read straight from Blade via `@json(config('hideout.bank_accounts'))` — no controller passes it. ⚠ The **selected bank is not persisted**; the transaction only stores `payment_method = 'transfer'`. `Owner\TransactionController:169`'s `$paymentLabels` now includes `transfer` → "Transfer".
- Alpine state for the bank modal (all three POS views): `showBankModal`, `bankAccounts`, `selectedBankIndex`, plus a `bankTransferPaid()` method. `proceedPayment()` (create views) opens the modal for `transfer` instead of jumping straight to the confirm modal.
- `config/hideout.php` is the only app-specific config file; the `bank_accounts` values are placeholders — the owner must replace them with the real store accounts.
- When the hidden `print_receipt` input is truthy, `store()` returns the PDF response directly instead of redirecting; otherwise it redirects back with a `success` flash rendered as a Swal toast.
- POS cart state persists in `localStorage` under `pos_cart` / `pos_state`, cleared by `confirmLogout()`.

### Two independent PDF code paths

1. **Receipts** → `App\Support\ReceiptBuilder::toResponse()`, rendering `views/pdf/receipt.blade.php` on 80mm thermal paper, returned `inline` (browser preview). DomPDF has no content-height API, so it **binary-searches the smallest single-page height** — don't "simplify" that. Used by `receipt-pdf` on both roles and by `store()`.
2. **Transaction report** → `Owner\TransactionController::printIndex()` builds a **raw `new Dompdf`**, A4 landscape, view `owner.transactions.print` (route name is `owner.transactions.print-index`) → `laporan-transaksi-*.pdf`. Don't route this through `ReceiptBuilder`.

### Route ordering is load-bearing

`Route::resource(...)` registers `show` at `/{param}`, which swallows any literal route registered **after** it. Register literal routes **before** their resource.

- `menus.load-more` (`routes/web.php:59`) is registered **after** `Route::resource('menus', ...)` (line 57) — so `GET /owner/menus/load-more` is dead (404). No view calls it: `owner/menus/index` inlines cards grouped by category with no pagination, and `owner/menus/_cards` is rendered only by the unreachable `MenuController::loadMore()`.
- On both owner and kasir, `receipt-pdf` and `load-more-menus` are correctly registered **before** `transactions/{transaction}`. Keep it that way.

## Known bugs (verified, unfixed)

Do not "fix" these blindly — confirm they still exist first.

1. **Promo double-application multiplies the discount.** In `store()` (both roles) the loop over `applied_promos` does `$promoDiscount += $serverAmount` on every iteration while `$appliedPromosData[$promo->id] = ...` dedupes by id, and `transaction_promos` has no unique constraint. Posting the same `promo_id` N times charges the discount N times but writes one pivot row — `pdf/receipt.blade.php` then prints the pivot value at `:96` and the multiplied total at `:107-110`, which cannot reconcile. Validation permits duplicates.
2. **Manual transaction discount is uncapped and fully client-controlled** (`'discount' => 'nullable|numeric|min:0'`, read at `Owner/TransactionController.php:471` / `Cashier/TransactionController.php:129`). `min:0` is a floor, not a ceiling, and `$total = max(0, ...)` floors at zero, so a kasir can post `discount=<subtotal>` for a free completed transaction. The careful promo recalculation in `calculatePromoDiscount()` does not cover this path. **Per-item** discounts *are* capped server-side (`min((float) $item['discount'], $menu->price * $item['quantity'])`, Owner `:435` / Cashier `:93`) — don't "fix" that one. `promos.value` is capped at 100 for percentage type.
3. **`CashierController` route-model binding is not scoped to the kasir role.** `index()` filters `User::role('kasir')`, but `edit`/`update`/`destroy`/`toggleStatus` (`:75,80,122,134`) take a bare `User $cashier` with no `hasRole('kasir')` assertion — so `PATCH /owner/cashiers/{anyUserId}` can rewrite the owner's own account. `destroy()` soft-deletes (see *Domain notes*) and refuses self-delete, but can still soft-delete the owner by posting another user id. Owner-only, so lateral movement rather than privilege escalation.
4. **Stats ignore `status` inconsistently.** `Owner\TransactionController::historyStats()` / `transactionsStats()` (`:573`, `:174`) default to `where('status', 'completed')` but use `$request->status` when supplied, and `$request->status` is never validated. `Cashier\TransactionController::historyStats()` (`:236`) hardcodes `completed`. Both render the same `cashier.transactions.history` view, so owner and kasir see different "Total Pendapatan" for identical rows. `page()`'s `$todayTransactions` (`:60`) also omits the `completed` filter that its sibling `$todayRevenue` has.
5. **Inactive menus stay sellable.** Every *read* path filters `Menu::where('status','active')`, but `store()` uses `Menu::findOrFail()` with no status check — a cart already in `localStorage.pos_cart` when the owner toggles a menu off will still sell it. (`Menu` uses `SoftDeletes`.)
6. **Silent stale-promo drop.** `if (! $promo) { continue; }` when a promo expires between page load and submit. The cashier only sees "Jumlah bayar kurang dari total." and the cart keeps showing the old discount, so retries fail identically.
7. **Client trusts `localStorage`-cached `category_id`/`price`, server re-reads the DB.** Moving a menu to another category or editing its price under a live cart makes the client and server disagree, producing the same misleading payment error as #6.
8. **`bindHistoryEvents()` is re-called on every `fetchHistory()`** (`cashier/transactions/history.blade.php:344`; defined at `:375`), attaching duplicate listeners each filter run. Not user-visible (a shared debounce collapses them) but listeners grow unbounded. Affects both roles (owner renders the same view).

- **Registration is dead**: `RegisteredUserController` validates/creates `name`, and `resources/views/auth/register.blade.php` does not exist even though `GET /register` is routed.
- **The dev DB is fully migrated and seeded** (re-verified 2026-10-21: 26/26 migrations Ran, 21 tables in `hideout_coffe`; users `mhdhsbyy`/`zein`/`daniel`). ⚠ `docs/erd.md`'s header warning that the DB is half-migrated (5/19) is **stale**. - **⚠ The MySQL server is SHARED with unrelated apps** — `php artisan db:show` reveals sibling databases (`binaku`, `minimarket_jayusman`, …) alongside `hideout_coffe`. Server is MySQL 8.4.3, user `root`, empty password. Only `hideout_coffe` is yours; never point `DB_DATABASE` at a sibling schema and never run `migrate:fresh` while another app is running.
- **MySQL is not a Windows service — it ships with Laragon** (`C:\laragon\bin\mysql\mysql-8.4.3-winx64\bin\mysqld.exe`) and may not be running. Symptom: every artisan command fails with `Connection refused` on `127.0.0.1:3306`. Start Laragon (or `mysqld`) first — because session/queue/cache are all `database` driver, the *whole app* 500s without it, not just DB writes.
- **`README.md` is stock Laravel boilerplate** and documents nothing about this app. This file is the source of truth. `docs/` holds hand-written `class-diagram.md` + `erd.md` (untracked by git) — read them for schema/entity orientation before inventing new relations.
- **`.env.example` diverges from `.env`**: the example ships `DB_CONNECTION=sqlite` (MySQL host/port/db/user all commented out) and `APP_LOCALE=en`, vs MySQL `hideout_coffe` + `APP_LOCALE=id` in `.env`. Uncomment and switch before migrating.
- **Tailwind is v3 only.** `postcss.config.js` runs `tailwindcss` + `autoprefixer` and `resources/css/app.css` uses `@tailwind` directives. `@tailwindcss/vite` (v4) is in `package.json` but is **not** wired into `vite.config.js` — do not use v4 syntax (`@import "tailwindcss"`, CSS-first config).
- **Never re-add the `storage/framework/views/*.php` glob to `tailwind.config.js`.** It used to be there; after `php artisan view:clear` the empty directory made the CSS build die with `ENOENT` and *no* Tailwind styles applied until `view:cache`. The glob is now gone. If styles ever vanish after clearing views, run `php artisan view:cache` or restart `npm run dev`.
- **Seeder order matters**: `DatabaseSeeder` calls `UserSeeder` first because it `firstOrCreate`s the `owner`/`kasir` roles; the other seeders depend on those roles and categories. `TransactionSeeder` **is** wired in (5th) and `delete()`s every transaction before re-seeding. `UserSeeder` also `delete()`s the stale `hasby` username.
- **No CI** — there is no `.github/` directory, so nothing catches breakage on push.
- **⚠ The C: drive has run at 100% full (0 bytes free) — this silently corrupts tooling.** It hit that on a past session: `./vendor/bin/pint` fataled with `phar error: internal corruption` / `No space left on device`. Space has since been freed (~15G free); if it re-corrupts, free space then `composer reinstall --dev laravel/pint`. Until space is freed, anything that writes (Vite build, view compilation, caches) can fail with ENOSPC — check `df -h` before debugging "mysterious" build errors.
- **`composer dev` is very slow on Windows** without OPcache (~1.3–2s TTFB on even a bare `/up`). That is the PHP built-in server recompiling, *not* a slow query. Enable `zend_extension=opcache` + `opcache.enable_cli=1` in `php.ini` (`php --ini` to locate) and restart; a warm `/up` drops to ~0.25s.
